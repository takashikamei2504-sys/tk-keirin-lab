# 展開を語るLAB：本線を先に考える

公開画面は `story-first-v4.0.0`。主役を一本の展開仮説に戻し、買い目はその帰結として選ぶ。旧v1.2、元v1.3、旧独立エンジンv1/v2は保持する。

## 6段階

1. 想定並びとS取り。番手・3番手のS取りからライン先頭を迎え入れる場合も生成。配信上の並びと、同一出走表の選手コメントが矛盾する場合は予想を停止する。
2. 赤板から打鐘。どのラインが抑え／カマシへ行くか、前受けが出させるか突っ張るか、その結果どこが前に出るかを分ける。
3. 最終ホーム。一本棒に落ち着くか、別線がロング捲りへ行くか。すんなり追走と離れを分ける。
4. 最終バック。主導権、一本棒／併走／隊列の切れ目、空いた番手の利用を保持する。
5. 最終3～4コーナー。外からの捲りに番手がブロックするか、横へ動かず縦を踏むか。ブロックで内が空いた場合だけ中割り／イン突きの候補を作る。
6. 直線。先行の消耗、番手の仕事・温存、外の勢い、内の進路から決着候補を作り、本線の結論を語る。差し／逃げの入れ替わりも同じ展開内の6点に含める。

状態の順番を守り、隊列は全員の順列を維持する。隣接する位置の入替えを記録するが、車間・速度・物理的到達時間は未計測。文章だけを後付けする仕組みではなく、同じ状態遷移から本文と買い目を出力する。ただし判断係数は未校正のルールで、学習済み言語モデルによる自由読解ではない。

## 本線6点と別筋4点

Sを取る選手が違っても同じ隊列に落ち着く場合は、同じ戦術状態へ重みを合流させる。6段階を通る候補を比較し、**決着買い目を集約して順位付けする前に、本線ストーリーを決める**。

本線6点はすべて同じストーリーに対応する。別筋は赤板、ホーム、3～4角、S取り・初手の判断が変わる候補から、異なる買い目を1点ずつ4点選ぶ。成立する候補の中に本線と1着が違う筋を含める。「穴候補」は展開上の意味で、実際のオッズの高さを確認した表示ではない。各買い目から元のストーリーへ戻れ、同じ1・2着はまとめて表示する。

## 情報収集

- 公開日別出走表：氏名、登録番号、得点、脚質、並び、期別、登録地、級班。提供元の印・予測・買い目はモデル入力に渡さない。
- KEIRIN.JP：全現役S級を対象とした近況成績・Bの収集を継続。
- 東スポの公開出走表：観測したリンクだけを辿り、S/Bの見出しを照合して直近4ヶ月のSを取得。選手名・車番・登録地・級班を検査し、公式全S級名簿との一致が取れた選手は登録番号でも結合する。本人コメントは選手別見出しの範囲だけを使う。
- 公開記事・インタビュー：前受け、突っ張り、引き、カマシ、捲り、追走等に、ブロック、縦踏み、内のコース、ホーム捲りを追加。本人発言から過去の援護への謝意、師弟、信頼を抽出する。姓だけの解決は同一の出走者の中で一意な場合に限る。

Sとコメントは `data/race_material.json`、記事・関係発言は `data/intelligence.json`。記事収集の実行後、最大24出走表・90秒を追加予算として収集する。S級の出走表では観測した他Rのリンクを優先する。robots・サイトの応答・構造変更により取得できないものは欠損のまま保持する。全S級のS実測が揃ったという意味ではない。

出走表内の欄外記事が `article:published_time` を持つため、その日時を出走表の公開日時に流用しない。出走表の対象日と初回取得時刻を別に保存し、コメントの公開時刻が不明な場合は取得時刻を利用可能時刻の保守的な上限にする。発走後の初回取得は過去の予想へ入れない。Sは同一レースの車番・フルネーム一致、または公式名簿との同一性が確認できた選手に限り72時間以内の観測を使う。

先輩（期別）、級班上位／得点上位、地元（登録地と開催地）は確認できる登録上の情報。「だから先行意欲が高まる」は弱い推測として分離する。「前に世話になった」等の実際の発言はURL・話者・相手・取得時刻を残し、根拠がなければ創作しない。今日の「自力」「先行」等は対象レースだけの意思表示として扱い、恒常的な性格へ加算しない。

## 保存・評価

新しい10点と過去の20点の記録を区別し、過去の買い目を書き換えない。共通予想には本線・別筋の6段階、Sの出典、関係発言、選択方針を保存する。旧エンジンとの比較は同じ入力・同じ点数に揃える。画面の成績はバージョン・点数別の内訳も表示する。結果から実際の攻防まで確定したとは扱わない。

確認コマンド：`npm test`、`python3 -m unittest discover -s tests -p 'test_*.py'`、`python3 scripts/build_page.py`。スマホ幅のテストで6段階、本線6＋別筋4、展開リンク、レース切替、JSON保存を確認する。

## v3.1：判断と根拠を同じ分岐から出す

当日コメントの先行・カマシ・捲り・番手からの発進意思は、同一レース・発走前の発言と確認できた場合だけ対応する選択肢の重みに反映する。過去インタビューの意向を今日の意思とは扱わない。否定・過去形・途中で切れた宣言は自動加算しない。本文観察による特性更新と今回の意思表示を分ける。

近況B比率、前段階で使った脚、現在位置、元のラインの番手か別線から入った番手かも分岐に使う。Bは長い先行の補助材料であって、追走力やS取りの実測ではない。消耗は状態遷移で置いた仮説値で、体調・実測の疲労ではない。

各段階に「この判断の材料・別の選択肢」を折り畳んで表示する。実際の重み付け時に作った同じ記録から、材料、推測、比較した選択肢、未取得情報、出典を出力・保存する。買い目から別の理由を後付けしない。係数は未校正で、学習済みの確率や的中率を示さない。

並びは「君へ」だけでなく「さんの後ろ」「君の番手」「単騎」「位置を決めず」「直付け・競り」を区別する。「後ろ・番手」は直前の選手まで照合する。曖昧な姓、条件付き・過去の発言を追走先の確定に使わない。同じ選手のコメントが更新された場合は最新の発走前観測だけを使う。競りは現在の一本のライン表現では未対応のため、確認を求めて生成を止める。

出走表の収集済みキャッシュからも観測済みの他Rリンクを辿り、未収集レースの探索を続ける。コメントの冒頭が同じでも最後の今回方針が変われば、別のスナップショットとして残す。

## v4.0：待機と反撃を問い直して本線を選び直す

従来の最大経路重みは、攻撃側だけに成功・併走・追走成否が増えるため、途中から動かない経路を過大評価していた。経路重みの保存と診断は続けるが、本線の選定は別の基準へ変更した。

- ホーム・バック・3〜4角の各地点で、全出走者の役割を列挙する。別線の自力選手は攻撃と待機の両方の理由を比較する。追走役・番手・先頭・進路制約・消耗により攻撃候補でない場合も、待つ理由を残す。
- 位置、先行側との脚力差（得点由来の代理値）、この展開で使った脚、残る仕掛けどころ、連れている後続・登録上の関係・対象レースの意思表示を比較する。先行の踏み直し、番手のブロック／縦踏み、第三ラインの追随を抵抗として見積もる。位置も消耗も観測事実ではなく仮説の状態。
- 相対的な攻撃価値を待機と比較し、より自然な反撃を無視する選択には比較上の不利を与える。低い能力・大きい消耗・遠い位置・進路制約なら待機を採る。全員を動かす規則ではない。ホームで待ってもバックで再評価する。
- バックの攻撃・成否・新しい先行の追走を追加。前段階の隊列をそのままバックへ複写しない。番手が離れた場合は後続を自動で番手に昇格させない。再自力する選手が元の先頭選手まで連れて前へ出ることも防ぐ。
- 経路の探索順位は、未処理の判断の異議、比較上の不利、情報による遷移の自然さで決める。枝を細かく作っただけで不利にならないよう、最大経路重みは優先基準にしない。
- 仕掛け・待機と番手応答の異議が残る経路、既に外にいる有力な攻撃を置き去りにした経路は本線から除外する。候補が残らない場合は探索幅を拡大し、それでも残らなければ生成を止める。棄却した本線を黙って採用するフォールバックは設けない。
- 最終的な本線は着順買い目を作る前に一つ選び、選考記録、各選手の比較、反撃への見立てとともに保存する。買い目の点数・配分ルールは変更しない。

これは観測されていない速度・車間を再現する物理シミュレーターでも、全選手の同時最適応答を解くゲーム理論モデルでもない。一つの局面では主な攻撃を選び、他の攻撃への抵抗と次の再評価を行う有限探索。係数・待機との比較尺度・許容差は手作業の未校正規則。検討済みという記録は実レースで成立する証明や的中確率を意味しない。強い言い方へ置換しただけではなく、比較・状態遷移・本線の採用基準そのものを変更した。

## Phase 4：買い目を上限10点へ柔軟化（v5.4）

本線の選定・6局面・モデル図は維持する。本線は決着比較の首位に対する相対支持0.65以上から最大6点。別筋は全体戦術評価が本線との差0.12以内で反証を通過した経路を再評価順に比較し、異なる分岐理由ごとに1点、最大4点。別筋内でも首位の0.65未満の着順は拾わない。候補が足りなくても10点へ埋めず、穴を演出する必須枠も置かない。これは未校正の設計基準であり、的中確率・EV・回収率最適化を意味しない。

実際の本線・別筋・合計点数を画面、コピー、JSON、保存・点数別集計に通す。既存10点/20点の履歴、凍結基準、発走前記録は更新しない。同一入力の研究比較は点数が異なるため的中率の優劣比較にはしない。

継続順：Phase 0〜3は統合済み。Phase 4のCI通過・統合後にPhase 5（記事本文の状況別特性と判断への接続）を実装する。Phase 6の指定は確認されていない。
